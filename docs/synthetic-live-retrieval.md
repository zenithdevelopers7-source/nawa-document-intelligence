# Synthetic live retrieval experiment

The offline BM25 index is a snapshot. An index constructed before an access or source change can continue returning an old passage. `SyntheticLiveRetrieval` experiments with rebuilding from callback-provided eligible passages and rechecking the principal and filtered snapshot before returning search results. Resolving a passage ID takes a fresh snapshot and rechecks it again. Synthetic tests cover two tenants with positive controls, a replaced version, withdrawal, identity changes and dependency errors.

The first callback tests use in-memory fixtures. The loader must itself establish the current approved source and exclude withdrawn or obsolete versions. The experiment has no production endpoint, authorization of exports, independent evaluation or production identity provider. Re-reading snapshots does not prevent a change after the final check; without a suitable generation marker, a change that occurs and reverts between checks can be missed. This is not a production authorization boundary or release gate. Do not use it to justify returning real or confidential data.

An additional disposable PostgreSQL experiment supplies the callbacks from local membership, tenant and version records. It admits only the latest explicitly versioned, completed, promoted and approved TXT source, validates the review ledger and checks retained bytes against the stored digest. It fails closed if a newer version exists without approval or a retained source is altered. Synthetic-only migrations add one-way withdrawals and explicit per-document view grants. In this test policy, a current reviewer manages grants for current members, with hashed actor and subject plus a reason in synthetic events; no grants are inferred for existing records. Grants bind to membership, identity and tenant generations, so an account state change requires a fresh grant. Withdrawals exclude the withdrawn version without reviving an older version. These controls affect only this experimental retrieval path and do not delete source data. The reviewer delegation policy is not independently approved, and a database administrator can alter records; these are not tamper-proof audits or production migrations.

A separate synthetic grant generation allows the PostgreSQL loader to detect a revoke and regrant between its two checks even when the visible passages are the same. It does not eliminate other changes that revert between reads, changes after the final check, privileged tampering or generation rollback on restore. The migration is for disposable tests only.

A disposable backup/restore test characterizes a separate risk: restoring a backup made before a grant was revoked can bring that access back. The test manually disables all grants on a newly restored QA database, checks access is denied for both test tenants, and regrants one account for a positive control. This manual QA-only reset is not wired into a recovery service, does not establish operator authorization or coordinate application processes, and does not recover revocations, withdrawals or other decisions made after the backup. Do not apply the test reset to an existing database.

An opt-in draft handler exposes synthetic search and source lookup using the server-side session principal, and checks that it still matches the reloaded membership. These test endpoints use bounded JSON POST bodies rather than query-string search terms, and require the expected origin and a session-bound CSRF token. Tests exercise them with in-memory fixtures and disposable PostgreSQL. A separate CI-only configuration uses the disposable Keycloak stack to exercise browser sessions; fixture code administers grants directly and is not a grant-administration endpoint. Request bodies may still be captured by infrastructure, so logging and retention require review. The handler is not configured for the running portal; no grant-administration endpoint, UI, exports or external identity-provider synchronization is implemented. The experiment does not prove that extracted values or reviewer corrections are semantically correct. PostgreSQL and file reads are not atomic, and the general two-read race limitations still apply. The test uses disposable synthetic records only.
